 1. User calls the client (/login) endpoint.
 2. That makes a challenge, setting the RedirectUri to be the client's root endpoint (/) and specifying the challenge should be made under the custom authentication scheme.
 3. The custom authentication scheme is an OAuth flow with PKCE enabled, so the client generates a code_verifier, derives a code_challenge (SHA256 hash, base64url-encoded) and sets code_challenge_method to S256. A redirect is made to the server's (/oauth/authorize) endpoint with code_challenge and code_challenge_method in the query string.
 4. The (/oauth/authorize) endpoint is reached but it requires authentication. The server specifies that the login path to authenticate is (/login), so the server redirects to the (/login) GET endpoint.
 5. The (/login) GET endpoint is a dummy HTML page with a form that doesn't take any user credentials; it just has a submit button that when clicked makes a request to the (/login) POST endpoint.
 6. At the (/login) POST endpoint, the user is logged in and a cookie is created with a name claim.
 7. The (/login) POST endpoint redirects the user to the ReturnUrl, which is the server (/oauth/authorize) endpoint.
 8. The (/oauth/authorize) endpoint validates the inputs in the query string (including code_challenge and code_challenge_method), creates an authorisation code payload containing the challenge details, protects (encrypts and authenticates) it with IDataProtector, and passes the resulting opaque code in the query string in a redirect to the client's callback URI (/oauth/callback).
 9. The client callback URI is an internal implementation, so it does its thing and then makes a POST request on the back channel to the server's (/oauth/token) endpoint with the authorisation code and the original code_verifier in the request body as an application/x-www-form-urlencoded content type.
10. The (/oauth/token) endpoint receives the request, unprotects the authorisation code to retrieve the stored code_challenge and code_challenge_method, recomputes the challenge from the provided code_verifier using the stored method, and verifies they match. If the authorisation code is invalid or the challenge verification fails, a 400 (bad request) response is returned to the client with a JSON error in the body.
11. If the authorisation code is valid and PKCE verification succeeds, an access token is constructed (which in this case is a JWT) and a 200 response is returned to the client with the access token.
12. The client does its thing in its internal implementation and then calls our handler for the OnCreatingTicket event, where we grab the access token, decode the payload and map (copy) the claims to the local user.
13. The internal implementation finally returns us to the original RedirectUri; the client (/) endpoint, where the local user's claims are returned in the response.
